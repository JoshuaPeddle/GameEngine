# Mobile platform support

This work addresses PG-01, PG-05, PG-08 through PG-12, PG-14's suspended polling, PG-33 and PG-36 from the October 26, 2026 platform audit. Findings GE-106 through GE-114 track the changes. The demo heads and game template share the same contracts. Core has no dependency on UIKit, Android or Avalonia.

Android forwards activity start, resume, pause and stop to `App.Lifecycle`. iOS observes application and scene activation notifications from its app delegate because Avalonia owns the scene delegate. The browser forwards visibility, pagehide, pageshow, blur and focus. Desktop hosts can supply their own `HostLifecycle` through `GameView.Lifecycle`. A view subscribes on attachment and unsubscribes on detachment. Engines supplied by an embedder retain their existing ownership and presentation settings.

`Engine.SetHostState` accepts Active, Inactive or Background. `Engine.LifecycleChanged` reports Pause before Background, and Foreground before Resume. Repeated states do nothing. Returning to the foreground preserves a game's separate `SetRunning(false)` pause. The dedicated native loop blocks on a semaphore when inactive, backgrounded, paused, faulted or waiting for its first paint. The browser awaits the same signal asynchronously. Posting work, changing scenes, presenting the first frame, resuming and stopping wake the loop. Backgrounded engines defer posted game work until activation. The timing baseline resets on wake so suspended time does not become simulation catch-up. Native presentation pacing sleeps at normal thread priority rather than spinning. Mobile views default to 60 Hz simulation and presentation; borrowed engines retain their owner's rates. Browser foreground scheduling still uses the existing timer loop, so display-synchronized browser pacing remains PG-15.

A game can subscribe to `Engine.LifecycleChanged` during initialization and checkpoint when it receives Pause or Background. Callbacks run synchronously on the thread applying the host transition, under the same lock as simulation. They finish after any current simulation step and before the platform callback returns. Keep handlers short, handle storage failures and unsubscribe when the subscription is no longer needed. An unhandled lifecycle callback exception records an EngineFault and still leaves foreground services disabled. The hook supplies a checkpoint boundary; it does not implement an idle game's save schema, offline settlement or process-death recovery.

Pointer events retain their existing position and default to contact ID zero for existing hosts. Avalonia supplies each pointer's contact ID, captures each pressed contact independently and reports capture through `IsCaptured`. `InputManager.Contacts` holds the current virtual position and capture flag for each delivered contact. Read it from simulation or pointer callbacks. A release ends only its own contact. Capture loss, focus loss, backgrounding and detachment produce Cancel events. Cancellation never produces a gesture key. Moves are limited when the queue is busy; Press, Release and Cancel are retained in order. Terminal events are delivered even outside the viewport or after its dimensions become invalid. Captured moves extrapolate virtual coordinates beyond letterbox boundaries. Hover moves are delivered without a press.

Release-to-Space/WASD conversion defaults off and resets with a scene's input bindings. A scene that wants the legacy gestures sets `inputManager.ReleaseGesturesEnabled = true` in Initialize. Keyboard-driven demos opt in. Emberbrook, Void Bastion, Brick Breaker and the pointer demo use raw pointers. Physical keys and synthetic taps have separate input source IDs, so one contact or timer cannot release another source's held key. The WinForms runner also honors the opt-in setting.

Android Back reaches `Engine.BackRequested` through the attached GameView's TopLevel on both activity and single-view application lifetimes. A handler closes a panel or changes game state and sets `Handled = true`. Without a handler, the first request pauses the game; another request while paused returns control to Android's normal navigation. The host does not recreate the game view. Both Android manifests enable the framework's modern back callback. Avalonia 12.1.1 uses AndroidX OnBackPressedDispatcher on Android 13 and later and exposes the completed Back request. It does not expose predictive gesture progress to this game API. Predictive navigation animations and gesture cancellation still require an Android 16 device check. The inspected framework implementations are [AvaloniaActivity](https://github.com/AvaloniaUI/Avalonia/blob/12.1.1/src/Android/Avalonia.Android/AvaloniaActivity.cs) and [BackPressedCallback](https://github.com/AvaloniaUI/Avalonia/blob/12.1.1/src/Android/Avalonia.Android/BackPressedCallback.cs).

`Engine.HostServices` exposes optional keep-awake and haptics capabilities, unavailable reasons and user settings. Keep-awake defaults off. Set `KeepAwakeEnabled` for an active visible game. iOS uses IdleTimerDisabled, Android uses FLAG_KEEP_SCREEN_ON and browsers request a screen wake lock when available. A game pause, host deactivation, backgrounding, view detachment, engine fault, Stop or Dispose releases the request. Native calls run on the UI thread. Browser support, acquisition and denial are reported separately; a delayed grant is released if the game became inactive while it was pending. Visibility restoration can reacquire the lock. A browser or OS can still revoke a lock.

Haptics supports Placement, Rejection and Reward through `PlayHaptic`. `HapticsSupported` describes hardware capability. `HapticsEnabled` is the user's toggle, initially false and persisted in app-private mobile preferences. iOS uses UIImpactFeedbackGenerator for placement and UINotificationFeedbackGenerator for rejection and reward. On iOS 17.5 and later the impact generator is associated with the active view through the current API. Android uses native semantic feedback constants and respects the system's haptic setting. Requests are ignored while disabled, paused, detached, backgrounded or disposed. A true result means the request was accepted for UI-thread delivery, not that the person necessarily felt a vibration. Browser and desktop haptics report unavailable unless an embedder supplies a backend. A game should provide a settings control and request cues for deliberate actions rather than every particle hit.

Level metadata writes and reads use generated System.Text.Json metadata, including the level, entity and component DTO vocabulary. The builder no longer serializes anonymous types. Dynamic level values accept JSON elements, strings, booleans, numbers, `Dictionary<string, object>` and arrays or sequences of those values. Unsupported CLR objects fail explicitly; games can convert additional DTOs to JsonElement with their own generated context. Demo file and browser saves share EmberbrookSaveJson. `tools/MobileSerializationSmoke` publishes as NativeAOT with reflection serialization disabled and round-trips metadata, every builder component shape, level files and demo saves. CI runs that executable in Release.

Both iOS heads require iOS 15.0 and bundle PrivacyInfo.xcprivacy at the app root. Tracking is false and the collected-data and tracking-domain lists are empty. File timestamps use C617.1 for app-container files accessed by level and save IO, the runtime and SkiaSharp. System boot time uses 35F9.1 for elapsed intervals in Engine, Avalonia's display timer and its input timestamps. Disk space uses E174.1 for runtime file-write availability. UserDefaults uses CA92.1 for the app's haptics preference. These match the [.NET runtime/BCL required-reason inventory](https://github.com/dotnet/macios/blob/main/docs/required-reasons-bcl.md) and [Microsoft's manifest guidance](https://learn.microsoft.com/en-us/dotnet/maui/ios/privacy-manifest?view=net-maui-10.0). The MAUI framework itself is not a dependency.

The dependency inspection covered Avalonia.iOS 12.1.1 sources, SkiaSharp.NativeAssets.iOS 4.151.1 native imports and the built app bundle. Avalonia's DisplayLinkTimer and InputHandler use elapsed timing. SkiaSharp imports stat and fstat. Neither package supplies an additional xcprivacy file in this simulator app. Avalonia also contains an ActiveInputModes fallback in its text-input responder. The current canvas game has no text-entry fields, so no active-keyboard reason is claimed. A game that adds text editing must review that reachable path against Apple's text-field requirement for 54BD.1. Validate the final signed archive's privacy report and any added SDKs before submission. This simulator inspection is not App Store approval.

`tools/check-ios-privacy.py` compares the built manifest with its tracked source, checks the four required-reason entries, verifies the no-tracking declarations and checks MinimumOSVersion. Pass a built `.app` and `--expected` pointing to its head's PrivacyInfo.xcprivacy. The demo and copied template simulator apps were checked this way.

`tools/check-android-alignment.py` runs `zipalign -c -P 16 -v 4` on the delivered signed APK and inspects every packaged `.so` with `readelf -lW`. It checks every LOAD segment's alignment and virtual-address/file-offset congruence, including compressed libraries. Pass the signed APK, `--zipalign` and `--readelf`. CI runs this before the Android smoke test and before releasing APK artifacts. The [artifact report](10-android-native-alignment.md) identifies every inspected library. No incompatible dependency was found. APKs generated from a future AAB must be checked independently, and a 16 KB runtime remains a separate device or emulator gate.

Verification used SDK 10.0.403 and the iOS 27.0.10722 workload with Xcode 27.0 for iOS, and JDK 21 with Android SDK build-tools 36.0.0. Android and browser Debug builds and the full Release solution build completed. The iOS simulator Debug build completed with 12 upstream Avalonia linker warnings: 11 IL2037 generated dependency annotations and one IL2104 DesignerSupport warning. There are no engine serialization linker warnings, and those dependency warnings have not been suppressed. They remain a dependency/toolchain issue to review before a trimmed iOS store archive. The Release solution build excludes the iOS head in its existing solution configuration, so it does not replace that separate check.

Physical-device acceptance still includes home and lock transitions, incoming interruptions, repeated activation, multi-finger drags and capture loss, Back under gesture and three-button navigation, haptic feel and system suppression, screen dimming, and sustained foreground/background CPU measurement. Browser denial, release and delayed-grant paths have mock-based tests; Safari and Chromium hardware and permission behavior require live checks. Signed store archives, process death, game save recovery and a real 16 KB Android system have not been verified by these builds.

The final repository suites passed in Release: 313 Core tests, 244 Demo tests, 57 Editor tests and 12 Avalonia host tests, for 626 total. Four Node tests cover browser visibility, denial, revocation through visibility and late acquisition after release. The Release NativeAOT serialization executable passed with JSON reflection disabled. Android and browser Debug heads built with zero warnings. The full Release solution built with zero warnings. Both simulator privacy-bundle checks passed. The copied template consumed locally packed engine packages for its platform build checks.

In this restricted workspace, NuGet package and HTTP caches were redirected to `/tmp/ge-nuget` and `/tmp/ge-nuget-http`. Builds used `-p:UsedAvaloniaProducts=` to disable the build telemetry task, which otherwise attempts to write outside the sandbox. Android used an explicit JDK 21 directory, AndroidSdkDirectory and a temporary debug keystore. iOS used `DOTNET_ROOT=/Users/josh/.dotnet` with `/Users/josh/.dotnet` first on PATH, `-r iossimulator-arm64` and `-p:EnableCodeSigning=false`. These environment accommodations do not change the runtime platform implementations.

The copied template also passed all six of its headless tests. Its Android and browser Debug builds had zero warnings; its iOS simulator Debug build had the same 12 Avalonia linker warnings. The template's signed Debug APK passed the full native alignment check as well.
